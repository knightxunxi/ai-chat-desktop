# AI 聊天桌面应用需求说明

## 1. 项目背景

本项目是一个基于 C++ 的桌面 AI 聊天应用。用户可以在应用中配置 API Key、Base URL 和模型名称，然后通过兼容 OpenAI 接口格式的 AI 服务进行连续对话，例如 DeepSeek。

这个项目不仅用于实现一个可运行的软件，也用于学习企业软件开发的完整流程，包括需求分析、技术选型、架构设计、任务拆分、编码实现、测试验证、打包发布和版本迭代。

## 2. 项目目标

### 2.1 产品目标

- 实现一个类似常见 AI 聊天软件的桌面应用。
- 支持用户配置 API Key、Base URL 和模型名称。
- 支持与 AI 模型进行多轮连续对话。
- 支持流式输出，让 AI 回复逐步显示。
- 支持本地保存配置和聊天记录。
- 建立清晰、规范、可维护的 C++ 项目结构。

### 2.2 学习目标

- 理解企业项目从需求到交付的完整开发流程。
- 学习如何编写需求文档、技术方案和任务拆分。
- 学习使用 C++、Qt 6 和 CMake 开发桌面应用。
- 学习 HTTP API 调用、JSON 处理、流式响应解析、本地存储和错误处理。
- 练习模块化设计、版本控制、测试验证和迭代开发。

## 3. 目标用户

- 正在学习 C++ 桌面开发的开发者。
- 希望使用轻量级桌面 AI 聊天客户端的用户。
- 希望通过实战项目理解企业软件开发流程的学习者。

## 4. 项目范围

### 4.1 V1 范围

V1 目标是完成一个最小可用版本。

- Windows 桌面应用。
- 使用 Qt 6 构建图形界面。
- 使用 CMake 管理项目构建。
- 支持 DeepSeek/OpenAI 兼容接口。
- 支持设置 API Key、Base URL 和模型名称。
- 支持一个当前会话内的多轮对话。
- 支持 AI 回复流式输出。
- 支持本地保存和读取用户配置。
- 支持本地保存和恢复聊天记录。
- 支持基础错误提示和请求状态显示。

### 4.2 V2 范围

V2 目标是增强使用体验。

- 支持多个聊天会话。
- 支持会话重命名和删除。
- 支持 Markdown 渲染 AI 回复。
- 支持复制消息内容。
- 支持停止生成。
- 优化空状态、加载状态和错误状态。
- 增加基础日志能力，方便排查问题。

### 4.3 V3 范围

V3 目标是增强扩展性。

- 支持多个 API 服务商预设。
- 支持温度、最大 token 等高级模型参数。
- 支持系统提示词配置。
- 支持导出聊天记录。
- 改进 API Key 本地存储安全性。
- 增加更完整的自动化测试。

### 4.4 V1 暂不包含

- 用户账号系统。
- 云端同步。
- 插件市场。
- 语音输入或语音输出。
- 移动端应用。
- 复杂提示词管理。
- 企业权限管理。

## 5. 功能需求

### 5.1 应用启动

- 应用启动后应显示主聊天窗口。
- 应用启动时应读取本地保存的配置。
- 如果用户尚未配置 API 信息，应用应允许用户打开设置窗口进行配置。

### 5.2 API 设置

- 用户可以输入 API Key。
- 用户可以输入 Base URL。
- 用户可以输入模型名称。
- 用户可以将配置保存到本地。
- 发送聊天请求前，应用应校验必要配置是否为空。

推荐默认值：

```text
服务商：DeepSeek
Base URL：https://api.deepseek.com
模型名称：deepseek-v4-flash
```

说明：`deepseek-chat` 是旧模型名，当前仍可兼容使用，但 DeepSeek 官方文档说明该名称将于 2026-07-24 弃用。V1 默认使用较新的 `deepseek-v4-flash`。

### 5.3 消息输入

- 用户可以在输入框中输入消息。
- 用户可以点击发送按钮发送消息。
- 用户可以通过快捷键发送消息。
- 空消息不能发送。
- 请求进行中时，界面应显示发送中或生成中的状态。

### 5.4 消息展示

- 应用应按时间顺序展示用户消息和 AI 回复。
- 用户消息和 AI 消息应使用不同的视觉样式。
- 发送或接收新消息时，消息区域应自动滚动到最新内容。
- AI 流式回复应逐步显示在界面中。

### 5.5 多轮上下文

- 应用应在内存中维护当前会话上下文。
- 用户发送新消息时，请求中应包含当前会话的历史消息。
- 应用应支持清空当前会话。

### 5.6 本地存储

- 应用应保存 API 配置。
- 应用应保存聊天消息。
- 应用重启后，用户应可以恢复之前的聊天记录。

### 5.7 错误处理

- API Key 缺失时，应用应显示明确提示。
- 模型名称缺失时，应用应显示明确提示。
- 网络请求失败时，应用应显示明确提示。
- API 返回错误响应时，应用应显示明确提示。
- 请求失败不应导致应用崩溃。

## 6. 非功能需求

### 6.1 可维护性

- 项目应采用分层架构。
- UI、业务逻辑、API 调用和本地存储应分离。
- 代码命名和格式应保持一致。

### 6.2 可扩展性

- API 客户端应围绕 OpenAI 兼容接口设计。
- 后续添加新服务商时，不应重写 UI 层代码。
- 聊天记录存储方案应具备可替换性。

### 6.3 安全性

- API Key 不能硬编码在源码中。
- API Key 不能提交到版本控制系统。
- V1 可以先使用 Qt 本地配置能力保存 API Key，但后续版本应考虑加密存储。

### 6.4 可靠性

- 网络失败应被优雅处理。
- 无效 JSON 响应应被优雅处理。
- 网络请求不应阻塞 UI 线程。

### 6.5 易用性

- 主界面应参考常见 AI 聊天软件布局。
- 核心操作应直观，不依赖说明文档。
- 错误信息应使用用户可以理解的语言。

## 8. 验收标准

V1 满足以下条件时，可以认为开发完成：

- 项目可以通过 CMake 成功构建。
- 应用可以启动并显示主窗口。
- 用户可以打开设置窗口并保存 API Key、Base URL 和模型名称。
- 应用重启后可以读取上次保存的配置。
- 用户可以向 DeepSeek/OpenAI 兼容接口发送消息。
- AI 回复可以显示在聊天窗口中。
- AI 回复可以以流式方式逐步展示。
- 连续对话时，请求可以携带历史上下文。
- 聊天记录可以保存到本地并在重启后恢复。
- 配置缺失、网络失败、API 错误响应时，界面可以显示清晰提示。
- 等待 AI 回复期间，界面保持可操作，不出现卡死。

## 9. 关键风险

### 9.1 API 兼容性风险

不同服务商虽然都声称兼容 OpenAI 接口，但请求字段、鉴权方式或流式返回格式可能存在差异。

应对方式：

- V1 先以 DeepSeek 为主要目标。
- 服务商差异收敛在 Service 层。
- 后续通过服务商预设扩展。

### 9.2 流式解析风险

流式接口通常基于 Server-Sent Events。解析不当可能导致文本丢失、重复显示或响应中断。

应对方式：

- 将流式解析逻辑封装到独立组件。
- 使用样例响应数据做解析测试。

### 9.3 UI 与业务逻辑耦合风险

如果把网络请求和数据处理直接写在窗口类里，后续维护和扩展会变困难。

应对方式：

- UI 层只负责展示和用户交互。
- API 调用放在 Service 层。
- 层与层之间通过 Qt 信号槽或清晰接口连接。

### 9.4 API Key 存储风险

V1 使用本地配置保存 API Key 比较方便，但安全性有限。

应对方式：

- 不在源码中硬编码 API Key。
- 不将真实 API Key 提交到 Git。
- 在后续版本考虑系统凭据管理或加密存储。

### 9.5 需求膨胀风险

AI 聊天应用很容易不断增加功能，导致第一版迟迟无法完成。

应对方式：

- V1 只实现最小可用版本。
- 增强体验和高级能力放入 V2/V3。
- 每个版本都明确“做什么”和“不做什么”。

## 10. 开发流程建议

本项目建议按以下流程推进：

1. 编写需求说明。
2. 编写技术方案。
3. 编写任务拆分。
4. 初始化 Git 仓库和项目骨架。
5. 按任务逐步实现功能。
6. 每完成一个功能就进行验证。
7. 完成 V1 后进行打包、测试和复盘。

每个功能任务都应包含：

- 明确的需求来源。
- 清晰的实现范围。
- 可执行的验证方式。
- 简短清楚的 Git 提交信息。
