# Agent 自更新方向优化

> 创建日期：2026-06-05  
> 状态：设计讨论稿，待实施  
> 目标：让 Agent 能从自身错误中学习，持续提升能力

---

## 一、核心理念

传统的 Agent 是"一次性"的——离线开发 → 发布 → 使用，运行期间行为固定。  
**自更新 Agent** 在运行过程中发现问题、记录分析、自我修正，形成持续进化的闭环。

## 二、架构方向：双 Agent 互审 + 共享记忆

### 2.1 为什么不能"自己改自己"

自我修改的一致性问题：

```
Agent v1.0 有 bug
  → Agent v1.0 修改自己的源码
  → 怎么知道改对了？——用同一个有 bug 的大脑验证自己的修改
  → 偏差累积 → 越改越差（模型坍缩 / Model Collapse）
```

### 2.2 双 Agent 互审架构

```
                  ┌──────────────────────┐
                  │  共享记忆 (MEMORY.md)  │  ← 唯一真相来源
                  └──────┬───────────────┘
                         │
          ┌──────────────┼──────────────┐
          │              │              │
    ┌─────▼─────┐  ┌─────▼─────┐       │
    │  Agent A  │  │  Agent B  │       │
    │  (提案者)  │  │  (审查者)  │       │
    │            │  │           │       │
    │ 执行任务   │  │ 验证提案   │       │
    │ 发现失败   │  │ 编译测试   │       │
    │ 写入提案   │  │ 批准/否决  │       │
    └───────────┘  └───────────┘       │
```

**工作流**：

```
1. Agent A 执行任务 → 失败
2. A 分析根因 → 写入记忆："PROPOSAL: 修改 X，因为 Y"
3. B 读取 PROPOSAL → 独立验证 X 是否真的有问题
4. B 执行修改 → 编译 → 跑相关测试
5. 测试通过 → B 写入记忆："APPROVED: proposal from A, tests pass"
6. B 代码合并 → A 重启（新版本）
7. A 读取记忆："上次的提案被通过了" → 用新代码重试
```

### 2.3 共享记忆约定

所有变更通过结构化区块记录：

```markdown
## 变更历史

### PROPOSAL-20260605-01
time: 17:30
author: Agent-A
content: workspace.delete_file 描述仍写"仅限工作目录"，与 V17.4 开放策略矛盾
file: src/tools/AgentToolRegistry.cpp
status: APPROVED

### APPROVED-20260605-01
time: 17:32
reviewer: Agent-B
proposal: PROPOSAL-20260605-01

### REJECTED-20260605-01

```

## 三、Self-Reflection 反射机制

### 3.1 嵌入位置

在 OODA 循环的 Evaluate 后增加 Reflect 节点：

```
OODA 循环（每轮）：
  Observe   → 读取上一步工具结果
  Orient    → 构建下一步提示词（含工具目录 + 观测 + 技能）
  Decide    → LLM 返回 action
  Act       → 执行工具
  Evaluate  → 收集 observation
  ┌─────────────────────────────────┐
  │ Reflect（新增）                  │
  │  toolResult.ok == false?        │
  │    是 → analyzeFailurePattern() │
  │    否 → 但输出不符合预期?        │
  │        是 → analyzeMismatch()   │
  │  写入 L3 记忆（带优先级标记）     │
  └─────────────────────────────────┘
  → 循环继续 或 done=true 退出
```

### 3.2 失败模式分类

| 模式 | 示例 | 自动修复策略 |
|---|---|---|
| 工具调用失败 | workspace.delete_file 返回"Protected" | 检查是否真的 protected，否则改描述 |
| 计划不完整 | 只生成 system.path 步骤，没有 delete | 强制 unified prompt 要求 COMPLETE plan |
| 权限/沙箱错误 | "Autonomous file operations must stay inside workspace" | 移除沙箱限制 + 更新工具描述 + 更新提示词 |
| LLM 返回格式错误 | JSON parse error | 注入 observation → 下一轮重试 |
| 认知不一致 | 工具执行成功但 LLM 说"未完成" | 双 Agent 互审：A 的判断 vs B 的验证 |

## 四、优先级调度更新

### 4.1 四级优先级

| 级别 | 触发条件 | 更新频率 | 更新内容 | 自动化 |
|---|---|---|---|---|
| **P0 致命** | 同一工具连续 3 次失败 | 立即（中断当前循环） | prompt 模板 / 工具描述 | 自动修复 |
| **P1 高频** | 同一工具跨会话 > 5 次失败 | 会话结束时 | 工具描述 / 参数校验 | 自动提案 + Agent B 审查 |
| **P2 低频** | 某场景未覆盖 / 新需求 | 每日汇总 | 新增工具 / 记忆注入策略 | 自动记录 + 人工确认 |
| **P3 优化** | 成功但低效（冗余步骤） | 每周 | 合并步骤 / 优化提示词 | 仅记录，人工决策 |

### 4.2 L3 记忆格式

```markdown
## 2026-06-05 reflect

### P0-20260605-01
tool: workspace.delete_file
failure: "Protected files and directories are rejected"
context: 用户要求删除桌面 123.txt，workspace.delete_file 拒绝非工作目录路径
hypothesis: 工具描述中"仅限工作目录"与 V17.4 开放策略矛盾
status: fixed — AgentToolRegistry.cpp 描述已更新

### P1-20260605-02
tool: system.path  
failure: LLM 只用 system.path 获取桌面路径，未生成后续删除步骤
context: Unified plan 只包含获取路径步骤
hypothesis: unified prompt 未要求 COMPLETE plan
status: fixed — AgentPlanPromptBuilder.cpp 提示词已更新

### P2-20260605-03
tool: N/A
observation: Agent 模式启动时弹窗"是否继续"体验差
suggestion: 改为自然语言"继续"命令触发，状态静默保存
status: fixed in V17.5
```

### 4.3 P0 自动修复流程

```
P0 触发 → 暂停当前 Agent 循环
  → Hook: OnCriticalReflection 触发
  → 运行修复子任务：
      1. 分析失败原因（调用 LLM）
      2. 生成修复方案
      3. 修改目标文件（工具描述/提示词/策略配置）
      4. 编译验证（cmake --build）
      5. 运行关联测试（ctest -R <related>）
      6. 通过 → 合并 + 从断点恢复循环
      7. 失败 → 回滚 + 标记为 P2 等人工处理
```

## 五、编译型语言的限制与策略

### 5.1 什么可以热更新

| 层 | 语言 | 可热更新 | 策略 |
|---|---|---|---|
| 模型层（提示词/记忆策略） | 文本/JSON | ✅ | 修改文件 → 重新加载 |
| Python 嵌入层（LLM SDK） | Python | ✅ | QProcess restart |
| UI 层 | C++/Qt | ❌ | 需要重编译 |
| 工具层 | C++/Qt | ❌ | 需要重编译 |
| 编排层（循环/解析） | C++/Qt | ❌ | 需要重编译 |

### 5.2 策略：热层自动更新 + 冷层标记提案

```
热更新（即时生效）：
  - prompt 模板文本
  - 工具描述 JSON
  - L3 记忆注入策略
  - Hook 脚本（Python）

冷更新（下次启动）：
  - C++ 源码修改 → 写入"待合并"提案
  - 用户手动编译 → 重新启动
  - 或：定时 CI 编译 → 替换二进制
```

## 六、与现有系统的集成点

| 现有系统 | 自更新中的作用 |
|---|---|
| OODA 循环 | Evaluate 后插入 Reflect 节点 |
| 三层记忆 (L1/L2/L3) | L3 存储 REFLECT 和 PROPOSAL，L2 存储已批准变更 |
| Hook 系统 | OnCriticalReflection（P0 触发）、PostTask（任务后反思） |
| Function Calling | system.self_reflect 工具 — 显式调用自我分析 |
| "继续" 命令 | 恢复中断的 Agent 循环（如 P0 修复后） |
| Agent 状态持久化 | 保存修复前后的状态快照，支持回滚 |

## 七、实施路线

| 阶段 | 内容 | 改动量 | 优先级 |
|---|---|---|---|
| **Phase 1** | Reflect 节点嵌入 OODA 循环 + L3 写入 | ~50 行 C++ | 高 |
| **Phase 2** | Agent B 审查模式（--reviewer 参数） | ~200 行 C++ | 中 |
| **Phase 3** | P0 自动修复（编译 + 测试 + 合并） | ~300 行 C++ | 中 |
| **Phase 4** | 优先级调度器（定时任务 + 会话结束触发） | ~150 行 C++ | 低 |
| **Phase 5** | 双 Agent 并行运行（QProcess 启动 B） | ~200 行 C++ | 低 |

## 八、面试可用的话术

> "我在 Agent 的 OODA 循环中嵌入了一个 Reflect 节点——每次工具执行后自动分析失败模式，按 P0-P3 优先级写入三层记忆。P0 级问题立即触发自动修复（修改配置 → 编译验证 → 测试通过 → 自动合并），P1 由第二个 Agent 实例独立审查后再应用。这比 LangChain 的 self-reflection 更进一步——不是同一个模型反思自己，而是双 Agent 交叉验证 + 版本化记忆作为唯一真相来源。"
