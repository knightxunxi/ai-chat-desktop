# AI 聊天桌面应用 V1 任务拆分

## 1. 文档目的

本文档用于将 V1 版本拆分成可以逐步开发、逐步验证的小任务。

每个任务都应尽量满足：

- 范围清晰。
- 可以独立提交。
- 有明确验收标准。
- 能支撑后续任务继续推进。

这份文档可以作为学习企业项目迭代开发的任务清单，也可以作为后续 Git commit、分支和开发记录的参考。

## 2. V1 总目标

V1 的目标是完成一个最小可用的 C++/Qt 6 桌面 AI 聊天应用。

V1 完成后，用户应该可以：

- 启动桌面应用。
- 配置 API Key、Base URL 和模型名称。
- 切换中文或英文界面语言。
- 发送消息给 DeepSeek/OpenAI 兼容接口。
- 看到 AI 的流式回复。
- 进行当前会话内的多轮对话。
- 为当前会话设置角色提示词，并让它影响 AI 回复。
- 关闭并重新打开应用后恢复配置和聊天记录。
- 在常见错误场景下看到清楚提示。

## 3. 任务分组

V1 拆分为 8 个阶段：

```text
阶段 1：项目基础
阶段 2：核心数据模型
阶段 3：主界面骨架
阶段 4：配置功能
阶段 5：聊天记录存储
阶段 6：AI API 接入
阶段 7：聊天流程集成
阶段 8：测试、打包与复盘
```

## 4. 阶段 1：项目基础

### TASK-001 初始化 CMake/Qt 项目骨架

目标：

- 创建 C++/Qt 6 项目基础结构。
- 让项目可以成功构建并启动空窗口。

主要工作：

- 创建 `CMakeLists.txt`。
- 创建 `src/main.cpp`。
- 创建基础目录：`src/app`、`src/core`、`src/services`、`src/storage`、`src/ui`、`resources`、`tests`。
- 配置 Qt 模块依赖：`Core`、`Widgets`、`Network`、`Sql`。

验收标准：

- CMake 配置成功。
- 项目可以编译。
- 启动后出现一个空的主窗口。

建议提交：

```text
feat: initialize qt project skeleton
```

### TASK-002 添加资源和基础样式机制

目标：

- 建立资源文件和样式加载机制。

主要工作：

- 创建 `resources/resources.qrc`。
- 创建 `resources/styles/app.qss`。
- 在应用启动时加载 qss。
- 加入最基础的窗口背景、字体、按钮和输入框样式。

验收标准：

- 应用启动后能加载样式文件。
- 修改 qss 后界面样式发生变化。

建议提交：

```text
feat: add resource and stylesheet support
```

## 5. 阶段 2：核心数据模型

### TASK-003 定义应用配置模型

目标：

- 定义 API 调用所需配置结构。

主要工作：

- 创建 `src/core/AppConfig.h`。
- 字段包含 `providerName`、`baseUrl`、`modelName`、`apiKey`。
- 字段包含界面语言 `language`。
- 提供 `isComplete()` 或类似方法判断配置是否完整。
- 提供默认 DeepSeek 配置值。

验收标准：

- 可以创建默认配置。
- 可以判断配置是否满足发送请求条件。
- 可以读取默认界面语言。

建议提交：

```text
feat: add app config model
```

### TASK-004 定义聊天消息和会话模型

目标：

- 定义聊天相关核心数据结构。

主要工作：

- 创建 `src/core/MessageRole.h`。
- 创建 `src/core/ChatMessage.h`。
- 创建 `src/core/ChatSession.h`。
- 支持用户消息、AI 消息、系统消息角色。
- 支持会话 ID、消息 ID、内容和创建时间。
- `ChatSession` 支持 `systemPrompt` 字段，用于保存当前会话的角色提示词。

验收标准：

- 可以在内存中创建会话。
- 可以向会话追加用户消息和 AI 消息。
- 可以为会话设置和读取角色提示词。

建议提交：

```text
feat: add chat session models
```

## 6. 阶段 3：主界面骨架

### TASK-005 实现主窗口布局

目标：

- 搭建类似常见 AI 聊天软件的主界面。

主要工作：

- 创建 `src/ui/MainWindow.h` 和 `src/ui/MainWindow.cpp`。
- 主界面包含左侧会话区域、右侧聊天区域、底部输入区域。
- 顶部或侧边提供设置入口。
- 提供当前会话角色提示词入口，可以先使用按钮或简洁编辑区。
- 底部包含输入框和发送按钮。

验收标准：

- 应用启动后显示完整主界面布局。
- 窗口缩放时布局基本正常。
- 发送按钮和设置按钮可点击，但可以暂不接入业务。

建议提交：

```text
feat: add main window layout
```

### TASK-006 实现聊天消息展示组件

目标：

- 实现消息展示区域和单条消息样式。

主要工作：

- 创建 `ChatView`。
- 创建 `MessageWidget`。
- 支持添加用户消息。
- 支持添加 AI 消息。
- 支持更新最后一条 AI 消息内容。
- 新消息出现时自动滚动到底部。

验收标准：

- 点击测试按钮或临时代码可以添加消息。
- 用户消息和 AI 消息视觉上可区分。
- 长文本可以正常换行。

建议提交：

```text
feat: add chat message view
```

## 7. 阶段 4：配置功能

### TASK-007 实现设置窗口

目标：

- 提供 API 配置输入界面。

主要工作：

- 创建 `SettingsDialog`。
- 输入项包含服务商、Base URL、模型名称、API Key。
- 提供界面语言选项，至少包含中文和英文。
- API Key 输入框使用密码显示模式。
- 提供保存和取消按钮。
- 保存前校验必要字段。

验收标准：

- 用户可以打开设置窗口。
- 用户可以输入并保存配置。
- 用户可以选择中文或英文界面语言。
- 必填项为空时显示提示。

建议提交：

```text
feat: add settings dialog
```

### TASK-008 实现配置本地保存

目标：

- 使用 `QSettings` 保存和读取配置。

主要工作：

- 创建 `ConfigStorage`。
- 实现 `load()` 和 `save()`。
- 应用启动时加载配置。
- 设置窗口保存后写入本地。

验收标准：

- 保存配置后关闭应用。
- 重新启动应用后可以看到上次配置。
- 重新启动应用后可以恢复上次选择的界面语言。
- 配置缺失时可以识别为未完成配置。

建议提交：

```text
feat: persist api settings
```

## 8. 阶段 5：聊天记录存储

### TASK-009 初始化 SQLite 存储

目标：

- 建立聊天记录数据库基础能力。

主要工作：

- 创建 `ChatHistoryStorage`。
- 初始化 SQLite 数据库连接。
- 创建 `sessions` 表。
- 创建 `messages` 表。
- `sessions` 表包含 `system_prompt` 字段。
- 确定数据库文件路径。

验收标准：

- 应用启动后可以创建数据库文件。
- 数据表可以自动创建。
- 数据库初始化失败时有错误提示或日志。

建议提交：

```text
feat: initialize chat history database
```

### TASK-010 实现聊天记录读写

目标：

- 支持保存和恢复当前会话。

主要工作：

- 保存会话信息。
- 保存当前会话角色提示词。
- 保存用户消息和 AI 消息。
- 加载最近会话。
- 支持清空当前会话。

验收标准：

- 发送过的消息可以写入数据库。
- 应用重启后可以恢复消息。
- 应用重启后可以恢复当前会话角色提示词。
- 清空会话后界面和数据库状态一致。

建议提交：

```text
feat: persist chat history
```

## 9. 阶段 6：AI API 接入

### TASK-011 定义 AIClient 接口

目标：

- 抽象 AI 客户端能力，为后续扩展其他服务商留入口。

主要工作：

- 创建 `AIClient` 抽象接口。
- 定义发送请求、接收文本片段、请求完成、请求失败、取消请求等能力。
- 明确信号槽或回调方式。

验收标准：

- UI 或控制层可以依赖接口，而不是依赖具体实现类。
- 后续可以添加新的 API 客户端实现。

建议提交：

```text
feat: define ai client interface
```

### TASK-012 实现流式响应解析器

目标：

- 解析 OpenAI 兼容接口的 SSE 流式响应。

主要工作：

- 创建 `StreamParser`。
- 支持解析 `data:` 行。
- 支持识别 `[DONE]`。
- 支持提取 `choices[0].delta.content`。
- 支持处理半包数据。
- 为解析器添加基础测试或测试样例。

验收标准：

- 给定样例 SSE 数据，可以提取文本片段。
- 多段响应可以正确拼接。
- `[DONE]` 可以被正确识别。

建议提交：

```text
feat: add streaming response parser
```

### TASK-013 实现 OpenAI 兼容 API 客户端

目标：

- 实现真实 API 请求能力。

主要工作：

- 创建 `OpenAICompatibleClient`。
- 使用 `QNetworkAccessManager` 发起 POST 请求。
- 根据配置设置请求地址和请求头。
- 根据当前会话消息构建 JSON 请求体。
- 如果当前会话存在角色提示词，将其作为 `system` 消息放在请求消息列表开头。
- 读取流式响应并交给 `StreamParser`。
- 处理 HTTP 错误、网络错误和 API 错误。

验收标准：

- 使用有效 API Key 可以收到 AI 回复。
- 错误 API Key 可以显示错误。
- 模型名称错误可以显示错误。
- UI 不被网络请求阻塞。

建议提交：

```text
feat: implement openai compatible client
```

## 10. 阶段 7：聊天流程集成

### TASK-014 实现 ApplicationController

目标：

- 连接 UI、配置、存储和 API 客户端。

主要工作：

- 创建 `ApplicationController`。
- 应用启动时加载配置和最近会话。
- 加载和更新当前会话角色提示词。
- 处理用户发送消息。
- 校验配置和输入内容。
- 创建用户消息和 AI 占位消息。
- 监听 AI 流式文本片段并更新会话。
- 请求完成后保存聊天记录。
- 请求失败时通知 UI。

验收标准：

- 主窗口不直接处理 API 细节。
- 发送消息流程可以完整走通。
- 请求成功和失败都能更新 UI 状态。

建议提交：

```text
feat: add application controller
```

### TASK-015 接入真实聊天交互

目标：

- 让用户可以通过界面完成真实对话。

主要工作：

- 将输入框、发送按钮和快捷键连接到控制层。
- 将角色提示词编辑入口连接到当前会话。
- 发送时禁用必要控件或显示生成状态。
- 流式更新 AI 消息。
- 请求完成后恢复输入状态。
- 空输入时禁用发送。

验收标准：

- 用户输入消息后可以看到自己的消息。
- 设置角色提示词后，后续请求会携带该提示词。
- AI 回复可以逐步显示。
- 连续发送多条消息时包含上下文。
- 请求中界面不卡死。

建议提交：

```text
feat: connect chat ui with ai client
```

### TASK-016 实现基础错误提示

目标：

- 处理 V1 必须覆盖的错误场景。

主要工作：

- 配置缺失提示。
- 网络失败提示。
- API 错误提示。
- 流式响应中断提示。
- 数据库初始化失败提示。

验收标准：

- 未配置 API Key 时不能发送，并提示用户配置。
- 网络断开时不崩溃。
- API 返回错误时界面显示清楚原因。

建议提交：

```text
feat: add basic error handling
```

## 12. 推荐开发顺序

建议严格按以下顺序推进，避免过早进入复杂功能：

```text
TASK-001 -> TASK-002
TASK-003 -> TASK-004
TASK-005 -> TASK-006
TASK-007 -> TASK-008
TASK-009 -> TASK-010
TASK-011 -> TASK-012 -> TASK-013
TASK-014 -> TASK-015 -> TASK-016
TASK-017 -> TASK-018 -> TASK-019 -> TASK-020
```

其中：

- `TASK-001` 是所有开发任务的基础。
- `TASK-012` 可以在真实 API 接入前完成，能降低流式解析风险。
- `TASK-014` 是整体集成关键点，完成后项目才真正从零散模块变成应用。
- `TASK-018` 是 V1 是否完成的最终判断依据。

## 14. 每个任务的执行方式

建议每个任务遵循以下小流程：

1. 阅读对应需求和技术方案。
2. 创建或切换到合适分支。
3. 完成当前任务最小实现。

## 15. V1 期间暂缓事项

以下事项很有价值，但建议不要打断 V1 主线：

- 完整插件系统。

## 16. 小工具集成的后续规划

后续可以在聊天功能稳定后引入小工具能力，例如文本总结、JSON 格式化、计算器、文件摘要、提示词模板等。

建议策略：

- V1 不实现完整工具系统。
- V1 代码结构中避免让 UI、API 和业务逻辑强耦合，为后续扩展留空间。
- V2/V3 再考虑增加 `tools` 模块和 `ToolRegistry`。
- 工具输入输出应标准化，避免每个工具都单独写一套流程。

潜在目录结构：

```text
src/tools/
├─ Tool.h
├─ ToolResult.h
├─ ToolRegistry.h
├─ ToolRegistry.cpp
├─ JsonFormatTool.h
├─ JsonFormatTool.cpp
├─ TextSummaryTool.h
└─ TextSummaryTool.cpp
```

这部分不作为 V1 必须完成内容，但会作为后续扩展方向保留在项目规划中。
