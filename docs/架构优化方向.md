## 三、详细设计

### 方向 1：本地小模型预处理 (P0)

**现状**：每次 Agent 循环，所有 observation、记忆、对话历史全量发给远程。工具返回 5KB 的文件内容也原样注入。

**问题**：
- observation 令牌消耗大（占每次请求 30-50% token）
- 记忆全量注入（L2+L3 可能数万字符）
- 没有输入端的注入检测

**方案**：在 Hook 层插入本地 Ollama/llama.cpp 调用

```
工具输出 → 本地 1B 模型 → 浓缩摘要(200字) → 注入到远程请求
三层记忆 → 本地小模型 → 只注入相关的 2 条
完整 prompt → 本地小模型 → 意图分类 → 决定是否带 tools
```

**收益**：
- 单次 Agent 循环 token 消耗降低 50-70%
- Agent 响应速度提升（更少的 token 意味着更小的网络包）
- 多一层注入检测（本地小模型可以识别并标记可疑内容）

**实现要点**：
1. 新建 `src/hooks/LocalModelHook.h/.cpp`（PreSend + PostReceive 两个 Hook）
2. 本地模型通过 `QProcess` 调 `ollama run qwen2.5:1.5b` 或 `llama-cli`
3. 设置超时 3 秒（超时则跳过，不阻塞主流程）
4. 配置化：模型路径、prompt 模板、启用开关放在 SettingsDialog

**风险**：
- 本地模型可能产生错误摘要（信息丢失）
- 增加 200-500ms 延迟（但总体可能更快，因为远程请求更小）

### 方向 2：多厂商适配层 (P0)

**现状**：`OpenAICompatibleClient::buildRequestBody()` 硬编码了 DeepSeek 的多模态格式（`{type: "image", image: {data, format}}`），且写死了 message 组装逻辑。

**问题**：
- 切换到 OpenAI/Gemini/Claude 需要改源码
- 图片格式不可互换（DeepSeek vs OpenAI 完全不同的 API 签名）

**方案**：抽象 `ModelAdapter` 接口

```cpp
// src/services/ModelAdapter.h（新增）
class ModelAdapter {
public:
    virtual QByteArray buildRequestBody(const AppConfig &, const ChatSession &,
                                        const QJsonArray &tools,
                                        const QJsonArray &images) = 0;
    virtual QString extractErrorMessage(const QByteArray &body) = 0;
    virtual bool supportsVision() const = 0;
    virtual int maxContextTokens() const = 0;
};

class DeepSeekAdapter : public ModelAdapter { ... };
class OpenAIAdapter   : public ModelAdapter { ... };
class AnthropicAdapter: public ModelAdapter { ... };
```

**收益**：
- 用户在 SettingsDialog 选择厂商 → 自动切 adapter
- 增加新厂商只需实现一个类（~100 行）
- 图片在未来多模态模型间无缝切换

**实现要点**：
1. `OpenAICompatibleClient` 持有 `unique_ptr<ModelAdapter>`
2. Factory 方法根据 `config.providerName` 创建对应 adapter
3. 保留一个 `GenericOpenAIAdapter` 做兜底

### 方向 3：ApplicationController 持续拆分 (P1)

**现状**：V18 已拆出 ConfigCoordinator、SessionCoordinator、AgentOrchestrator，但 ApplicationController 仍有 1700 行。

**残留职责**：
- 流式响应处理 (~150 行 handleTextDelta/handleToolUseBlockComplete/handleRequestFinished)
- 消息信号路由 (~100 行 connectController 链)
- 截图/图片粘贴处理 (~80 行 eventFilter + onImagePasted)

**方案**：再拆两个 Coordinator

```cpp
// 新: StreamCoordinator
// 负责: handleTextDelta, handleToolUseBlockComplete, handleRequestFinished
// 输入: OpenAICompatibleClient 信号
// 输出: textDeltaProcessed / toolBlockExecuted / agentLoopStepReady 信号

// 新: MediaCoordinator  
// 负责: 图片粘贴、截图、文件拖放
// 输入: MainWindow eventFilter
// 输出: mediaAttached(QStringList base64List)
```

**收益**：ApplicationController 降到 ~400 行（纯路由+初始化），每个 Coordinator 职责单一。

### 方向 4：工具并行执行 (P1)

**现状**：Agent 一次调用只能执行一个工具（串行）。如果有 3 个独立的文件读取操作，它们要排队。

**方案**：`AgentOrchestrator` 改造为并发执行

```
AI 返回: tool_calls = [read_a.txt, read_b.txt, read_config.json]
         ↓ 并行执行（无依赖）
    read_a.txt ─┐
    read_b.txt ─┼→ 等待全部完成 → 合并结果 → 注入 observation
    read_config ─┘
```

**实现要点**：
1. 用 `QtConcurrent::run` 或 `QThreadPool` 并行执行
2. 检测依赖关系（command.exec 可能依赖前一 command 的结果）
3. 结果聚合后按 tool_call_id 排序注入

**风险**：
- 命令执行工具也可能并行（多进程），需限制并发数
- 不确定 AI 是否预期串行执行

### 方向 5：跨平台支持 (P2)

**现状**：`#ifdef Q_OS_WIN` 遍布 InputSimulator、UiAutomationService、WindowsCredentialStorage、SendInput 等。

**方案**：抽象平台接口

```cpp
class PlatformService {
    virtual bool sendText(const QString &text) = 0;
    virtual bool captureScreen(const QString &path) = 0;
    virtual QString ocrText(const QString &imagePath) = 0;
    virtual void storeCredential(const QString &key, const QString &value) = 0;
};

class Win32Platform : public PlatformService { ... };
class MacPlatform   : public PlatformService { ... };  // CGEvent + Vision
class LinuxPlatform : public PlatformService { ... };  // xdotool + Tesseract
```

### 方向 6：真正的集成测试 (P2)

**现状**：67 个测试大多是单元测试 + UI 冒烟测试。Agent 循环的端到端行为（从用户输入到工具执行到 AI 回复）没有集成测试。

**方案**：Mock API 的集成测试框架

```cpp
// tests/integration/MockApiClient.h
class MockApiClient : public AIClient {
    // 预设 AI 回复:
    // 第1次: tool_calls → read_file("a.txt")
    // 第2次: 纯文本 "文件内容分析完毕"
};

// 测试: 完整 Agent 循环
void testAgentLoopCompletesTask() {
    MockApiClient mockClient;
    mockClient.setResponses({...});
    
    ApplicationController controller(&mockClient);
    controller.sendAgentLoopMessage("分析 a.txt");
    
    assert(controller.currentSession().messages.size() > 2);
    assert(mockClient.requestCount() == 2);
}
```

### 方向 7：测试框架从 assert() 迁移到 Catch2 (P2)

**现状**：`assert()` 失败直接 abort，一个 test exe 只能跑一个测试场景

**方案**：迁移到 Catch2（header-only，不增加构建依赖）

```cpp
TEST_CASE("Cron parser handles daily schedule") {
    TaskScheduler scheduler;
    auto result = scheduler.nextRunTime("0 9 * * *", QDateTime());
    REQUIRE(result.isValid());
    REQUIRE(result.time().hour() == 9);
}

TEST_CASE("Cron parser rejects empty input") {
    TaskScheduler scheduler;
    auto result = scheduler.nextRunTime("", QDateTime());
    REQUIRE(!result.isValid());
}
// 一个 exe 跑完所有场景，失败不中止，最后汇总
```

**收益**：
- 一个 exe 跑全部测试，失败继续
- 自动生成测试报告
- `REQUIRE` 比 `assert` 可读性好

### 方向 8：插件系统 (P3)

**现状**：Hook/Skill/MCP 提供了扩展点，但没有正式的插件生命周期。

**方案**：插件 = 一个动态库 (`.dll`/`.so`) + 一个 `plugin.json` manifest

```json
{
  "name": "code-reviewer",
  "version": "1.0",
  "hooks": ["PreSend", "PostReceive"],
  "tools": ["review_diff"],
  "skills": ["code_review.md"]
}
```

用 `QPluginLoader` 加载，实现标准接口：

```cpp
class CodexxPlugin {
    virtual QString name() = 0;
    virtual QVector<HookBase *> hooks() = 0;
    virtual QVector<AgentToolDefinition> tools() = 0;
};
```

## 五、技术债务清单

| 问题 | 影响 | 建议 |
|------|------|------|
| `markdownStyleSheet()` 硬编码颜色 | 暗/亮切换不完整 | 抽到 QSS 文件 |
| Token 估算粗糙 (`char * 1 + CJK * 2 / 3`) | 精度低 | 集成 tiktoken 或缓存 |
| `QEventLoop` 同步等 AI (AiLoopRunner) | 阻塞 UI 线程 | 全部改异步信号槽 |
| 重复 actor 检测基于 `QSet<QString>` | 误判风险 | 改为语义相似度 |
| MCP 连接器无 TLS/认证 | 安全问题 | 增加 API Key 传递 |
| 日志可能含 API Key | 安全泄露 | 增加日志 sanitization |
| `release/` 目录需要手动同步 | 部署复杂 | CI 自动打包 |
