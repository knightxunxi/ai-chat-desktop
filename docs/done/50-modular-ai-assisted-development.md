# 模块化AI辅助开发方法论

> 文档编号：50 | 创建日期：2026-06-21 | 作者：杨雄 | 版本：V1.0

---

## 一、背景与动机

### 1.1 问题

AI大模型在软件开发中存在两个核心瓶颈：

| 瓶颈 | 表现 | 后果 |
|------|------|------|
| **上下文窗口有限** | 项目规模超过5万token后，AI开始遗忘早期讨论的约束、忽略模块边界、生成与其他模块冲突的代码 | 修改Module A的代码，却破坏了Module B的接口 |
| **注意力稀释** | 一次性喂入过多文件和需求，AI无法聚焦当前任务 | 输出质量下降，细节错误增多，需要反复修正 |

### 1.2 核心思路

**用工程化的模块边界解决AI长上下文不可靠的问题。**

```
传统做法：喂整个项目 → AI上下文爆炸 → 输出质量差
本方法论：  只喂目标模块 → AI聚焦 → 高质量输出 → 自动化回归验证
```

## 二、方法论总览

### 2.1 五大原则

| 原则 | 说明 |
|------|------|
| **1. 模块隔离** | 每个AI会话只处理一个模块，绝对不跨模块修改代码 |
| **2. 文档驱动** | 每个模块有独立的Markdown文档描述其职责、接口、依赖 |
| **3. 接口契约** | 跨模块接口统一定义在 `INTERFACES.md`，任何修改需显式通知 |
| **4. 自动化回归** | 每次AI修改后立即跑全量CTest，零回归 |
| **5. 文档同步** | AI修改代码后必须同步更新对应模块文档 |

### 2.2 涉及的技术方向

| 方向 | 本方法论的实践 | 业界术语 |
|------|-------------|---------|
| 按模块隔离AI上下文 | 一个会话只处理一个子库 | **Context Window Management / Modular Prompting** |
| 文档描述模块行为，AI按文档改代码 | INTERFACES.md + 模块文档 | **Documentation-Driven Development** |
| 模块间通过接口定义解耦 | 改A不改B，接口签名不准碰 | **Contract-First Design** |
| 每次改完跑全量回归 | 改完→CTest→通过才接受 | **AI-in-the-Loop CI** |
| 多会话并行开发不同模块 | 子库A和B同时用不同会话开发 | **Parallelized AI Coding** |

### 2.3 适用于什么场景

| 适用 | 不适用 |
|------|--------|
| 项目有清晰的模块划分（如CMake子库） | 单体架构、所有代码在单个文件 |
| 模块间接口稳定、耦合度低 | 接口频繁变化的重构期 |
| 项目有自动化测试覆盖 | 测试覆盖率低于30%的项目 |

## 三、目录结构规范

### 3.1 项目级文档

```
project/
├── docs/
│   ├── INTERFACES.md          ← 核心！跨模块接口契约，绝对不能坏
│   ├── MODULE_A.md             ← 模块A的设计文档
│   ├── MODULE_B.md             ← 模块B的设计文档
│   └── MODULE_XX.md            ← 每新增模块对应一份文档
├── module_a/                   ← 模块A源代码
│   ├── CMakeLists.txt
│   ├── include/
│   └── src/
├── module_b/                   ← 模块B源代码
├── common/                     ← 共享类型定义、工具函数
│   └── include/common/types.h
├── tests/                      ← 跨模块集成测试
│   └── integration/
└── CMakeLists.txt              ← 顶层构建
```

### 3.2 单个AI会话的工作范围

```
本次会话权限：
  ✅ 可读写：module_a/ 下所有文件
  ✅ 可读写：docs/MODULE_A.md
  ✅ 可读取：docs/INTERFACES.md（只读参考）
  ✅ 可读取：common/include/（只读参考）
  ❌ 禁止修改：module_b/、common/、docs/INTERFACES.md
```

## 四、核心文档模板

### 4.1 INTERFACES.md（接口契约）

```markdown
# 跨模块接口契约

> ⚠️ 本文件是模块间通信的"宪法"。
> 任何修改此文件中定义的接口，必须：
> 1. 通知所有依赖该接口的模块开发者
> 2. 更新对应模块的单元测试
> 3. 跑全量集成测试验证

---

## Module_A → Module_B

### `int process_data(const std::string& input)`
- **所属文件**: `module_a/include/module_a/api.h`
- **输入**: 非空字符串，长度 1-4096
- **返回**: 0 成功，-1 输入无效，-2 内部错误
- **线程安全**: 否（调用方需自行加锁）
- **异常**: 不抛出
- **修改记录**: 2026-03-15 初版 | 2026-05-20 增加-2错误码

---

## Module_B → Module_A

### `void notify_result(int code, const std::string& message)`
- **所属文件**: `module_b/include/module_b/callback.h`
- **输入**: code (0成功，非0失败)，message (日志信息，可为空)
- **返回**: void
- **线程安全**: 是（内部已加锁）
- **调用时机**: Module_B处理完数据后回调
- **修改记录**: 2026-03-15 初版
```

### 4.2 模块文档模板（MODULE_A.md）

```markdown
# Module A - 设计文档

## 概述
简要描述模块职责（1-2句话）。

## 对外接口
| 函数 | 签名 | 说明 |
|------|------|------|
| process_data | `int(const std::string&)` | 处理输入数据，详见 INTERFACES.md |

## 内部架构
关键类/结构体及其关系（可用文字描述或ASCII图）。

## 依赖
| 依赖模块 | 用途 |
|---------|------|
| common/types | 使用 DataPacket 类型 |
| 无 | 无其他依赖 |

## 测试覆盖
| 测试文件 | 覆盖内容 |
|---------|---------|
| tests/module_a/test_process.cpp | process_data 的15个用例 |
| 覆盖率 | 92% |

## 变更日志
| 日期 | 变更 | 原因 |
|------|------|------|
| 2026-06-21 | 增加超时参数 | 解决长文本处理超时 |
```

## 五、AI会话System Prompt模板

### 5.1 单模块开发会话

```
# 角色
你是模块开发助手，只负责修改 [模块名] 的代码。

# 工作范围（严格边界）
✅ 可读写： module_[name]/ 下所有文件
✅ 可读写： docs/MODULE_[NAME].md（修改后同步更新）
✅ 可读取： docs/INTERFACES.md（只读，禁止修改）
✅ 可读取： common/ 目录（只读，禁止修改）
❌ 禁止修改： 其他模块、common/、docs/INTERFACES.md

# 工作流程
1. 先读 docs/MODULE_[NAME].md 了解当前模块状态
2. 再读 docs/INTERFACES.md 确认不会破坏接口契约
3. 实现需求，仅修改授权范围内的文件
4. 完成后运行 cmake --build build && ctest --test-dir build
5. 测试通过后，同步更新 docs/MODULE_[NAME].md

# 关键约束
- 绝对不要修改其他模块的接口签名
- 如果发现必须修改 INTERFACES.md 中定义的接口，在回复中明确告知我，由我决策
- 每次修改代码后，必须在回复末尾列出改动文件清单

# 当前任务
[任务描述]
```

### 5.2 跨模块协调会话（仅人执行）

当确实需要修改接口时，由人（而非AI）做决策：

```
步骤：
1. 在 INTERFACES.md 中标注接口修改计划（草案）
2. 通知所有受影响模块的AI会话："接口X即将变更，请暂停对该接口的依赖开发"
3. 人工决策后，先改接口定义和对应模块
4. CI跑通后，再逐个通知其他模块适配新接口
```

## 六、在CodeXX项目中的已有实践

### 6.1 现有架构与方法的映射

| CodeXX的做法 | 对应本方法论 |
|-------------|------------|
| 12个CMake子库（file/workspace/command/system/input/web/code） | **模块隔离**——每个子库独立编译 |
| ApplicationController拆分为 ConfigCoordinator / SessionCoordinator / AgentOrchestrator | **接口契约**——通过信号槽通信，Coordinator互不直接依赖 |
| 需求文档→任务拆分→分支开发→测试验证→合并复盘 | **文档驱动开发**——每一版都有roadmap + acceptance notes |
| 65个CTest全量覆盖，cmake build→ctest | **自动化回归**——每次提交验证零回归 |
| 分支开发，主分支保持稳定 | **单模块迭代**——一个分支对应一个功能模块 |

### 6.2 文档体系

CodeXX现有docs目录约50份文档，覆盖：
- 需求/设计/v1-v18各版本roadmap
- 验收笔记（每个版本的功能验证记录）
- 专项设计（agent安全、命令执行安全、skills/hooks设计）
- 架构优化方向、UI优化方向、重构方案

**这套文档体系本身就是"文档驱动开发"的实践。**

## 七、实战工作流

### 7.1 新功能开发流程

```
1. [人] 在docs/写需求文档 + 确定涉及哪些模块
2. [人] 如果涉及接口变更，先更新INTERFACES.md草案
3. [AI会话1] 读MODULE_A.md + INTERFACES.md → 实现模块A代码 → 跑CTest → 更新MODULE_A.md
4. [AI会话2]（并行）读MODULE_B.md + INTERFACES.md → 实现模块B代码 → 跑CTest → 更新MODULE_B.md
5. [人] 审阅两个会话的改动，合并，跑全量集成测试
6. [人] 确认INTERFACES.md最终版本，关闭会话
```

### 7.2 Bug修复流程

```
1. [人] 从测试日志/用户反馈定位问题模块
2. [AI会话] 读该模块文档 → 定位代码 → 修bug → 跑相关测试 → 更新文档
3. [人] 确认修复，跑全量测试
```

### 7.3 多会话并行规则

| 条件 | 可以并行 | 不能并行 |
|------|---------|---------|
| 两个模块无接口依赖 | ✅ | — |
| 两个模块有接口依赖但接口已稳定 | ✅ | — |
| 一个模块正在修改接口签名 | — | ❌ 另一个不能同时改 |
| 都在改 common/ 下的文件 | — | ❌ 会冲突 |

## 八、CI集成（自动化验证）

```bash
# 每次AI会话结束后运行的验证脚本
# .github/workflows/ai-module-verify.yml 或手动执行

# 1. 构建
cmake -B build -DCMAKE_BUILD_TYPE=Debug
cmake --build build -j$(nproc)

# 2. 单元测试
ctest --test-dir build --output-on-failure -j$(nproc)

# 3. 接口一致性检查（可选）
# 对比 INTERFACES.md 中声明的函数签名和头文件中的实际签名
python scripts/check_interface_consistency.py

# 4. 文档更新检查（可选）
# 检查本次修改的文件是否在对应模块文档中记录了变更
python scripts/check_doc_sync.py
```

## 九、效果评估

### 9.1 与一次性喂入的对比

| 维度 | 一次性喂入整个项目 | 模块化AI辅助开发 |
|------|------------------|----------------|
| 上下文质量 | 平均5-10万token，后半段注意力衰退 | 每个会话控制在2万token内 |
| 接口破坏概率 | 高（AI难以全局理解影响） | 低（接口契约约束+CTest快速发现） |
| 并行能力 | 无（单会话串行） | 多个独立模块可并行开发 |
| 代码回滚成本 | 高（改动分散，难以局部撤销） | 低（改动限定在单模块，可单独回滚） |
| 文档同步 | 极易遗漏 | System Prompt要求+检查脚本保证 |

### 9.2 适用规模

- 最佳：5-20个子模块，每个模块500-5000行
- 可行但需注意：3-5个模块，模块边界模糊时需要人为加强约束
- 不适合：所有代码在1-2个文件中的玩具项目

## 十、局限与待改进

| 局限 | 改进方向 |
|------|---------|
| 跨模块重构时成本仍高 | 需要人工协调多个会话，或由人手动完成 |
| 共享类型/common库的变更容易遗漏影响面 | 需要接口一致性自动检查脚本（待实现） |
| 模块文档的撰写和维护依赖人的自律 | 未来可用AI自动生成模块文档的初稿 |
| 多个AI会话并行时，人的审阅负担增加 | 通过更完善的自动化测试减少审阅量 |
