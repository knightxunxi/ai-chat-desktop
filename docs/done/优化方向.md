# AI Chat Desktop (Codex) 优化方向

向 Modern Agent 演进的优化方向分析。

**对标系统：** Claude Code / WorkBuddy / OpenClaw（小龙虾）/ OpenAI Codex CLI

**日期：** 2026-06-02 | **更新：** 2026-06-03（第九节深度对标分析）

---

## 2026-06-05 实施确认：当前优化边界

本节用于约束本轮代码优化，避免后续上下文窗口不足时误改方向。

### 不作为问题处理

1. **Workspace 默认高权限不是问题。** 本项目定位是个人本地 AI 桌面编程助手，Agent 默认拥有较高本机操作权限；不做“只允许工作目录内操作”的沙箱收紧。需要保留的底线是：不得修改 Windows 系统目录、系统关键文件、凭据/密钥等高危目标。
2. **图片粘贴暂不接入主发送路径不是问题。** DeepSeek 个人 API 当前暂未开放图像能力，现有 `sendMessageWithImages` 和粘贴缓存作为后续 Vision 模型备用入口保留。

### 当前优先实施项

1. **统一 Agent 执行入口。** 普通聊天和 Agent 模式可以并存，但 Agent 内部不应同时存在两套 UI 可达的自主循环。主 Agent 路径以 `ApplicationController + AgentOrchestrator` 为准；旧 `AgentLoopController` 仅保留为兼容/测试路径。
2. **修复 Function Calling 重复执行。** 流式工具参数完成时只缓存或只执行一次，不能在 `requestFinished` 再把同一批 `tool_calls` 转成计划重复执行。
3. **统一工具权限语义。** 默认高权限自动执行，但要让代码和文案一致：`requiresUserConfirmation` 不应误导测试和 UI；真正需要拦截的是系统关键文件、危险根目录和凭据类目标。
4. **修复 Scheduler 触发语义。** enabled task 应能按 cron 触发；调度任务不应直接取消用户正在进行的 Agent 请求。
5. **接通主 Agent 链路中的 Skills/Hooks/MCP。** Skills 匹配结果应进入主 prompt；Hooks 应覆盖主 Agent 生命周期和工具执行；MCP 工具应注册进 Agent 工具目录。
6. **持久化 Agent 新状态。** `agentSteps/branches/currentBranchIndex` 不能只存在内存里，至少应在存储层明确保存或显式标记为临时态。

### 验收要求

- 每个优化项需要配套最小测试，优先覆盖真实主路径，而不是只测私有状态。
- 每轮提交前运行 `cmake --build . -j4` 和 `ctest --output-on-failure`。
- 不为了“安全沙箱”牺牲本地 Agent 的默认高权限体验。

## 一、核心差距：Agentic Loop（最大优化点）

### 1.1 当前模式 vs 目标模式

**当前 Codex V7 — 线性「计划→执行」模型：**

```
用户目标 → AI生成JSON计划 → 解析 → 逐步确认 → 执行 → 结束 (最多再循环2轮)
```

**Claude/WorkBuddy — Agentic Loop「观察→思考→行动→观察」：**

```
         ┌─────── Observe ───────┐
         │  (工具结果/文件内容/状态) │
         ↓                        │
      Think                    Act
   (分析+决策)              (调用工具)
                                ↓
                           Evaluate
                        (判断是否继续)
```

### 1.2 具体差距

Codex 缺少的核心能力：

- **每步执行后自动重新观察、重新决策**，而不是按预先写死的计划机械执行
- **动态工具选择**：AI 能从工具目录中「自选」工具，支持模糊推荐，而非代码硬匹配
- **故障重规划**：工具失败后，AI 能建议替代方案（换工具 / 换参数 / 降级逻辑）
- **进度感知**：Agent 需要知道自己到哪了、还剩多少步、是否超时卡住

### 1.3 实现建议

在现有 `AgentPlanExecutor` 基础上改造：把 `executeStep` 从「单步执行 + 返回结果」改为「执行 → 把结果注入新 prompt → 再生成下一步」。本质上是去掉「一次生成所有计划」的约束，改为每步动态生成。

#### 改造后的执行流程

```
Step 1: Observe
  读取上一步 ToolResult (ok / output / error)

Step 2: Think
  把结果 + 原始目标 + 可用工具目录注入 AI prompt

Step 3: Act
  AI 返回下一步的 toolId + parameters（单步，而非全量计划）

Step 4: Evaluate
  本地校验 → 用户确认 → 执行 → 回到 Step 1

终止条件:
  - AI 返回 done=true
  - 达到步数上限 (maxSteps=5)
  - 用户点击停止
  - 单步超时 (30s/工具)
```

## 二、Function Calling 替代 JSON 解析

### 2.1 现状问题

当前 AI 返回的是普通文本中的 JSON，Codex 用 190 行的 `AgentPlanParser` 从 Markdown 代码块里提取解析。问题：

- AI 格式输出不稳定（有时缺字段、有时多文本干扰）
- 解析逻辑越来越复杂，维护成本高
- 与行业主流方式脱节（面试中会被追问为何不用 Function Calling）

### 2.2 建议方案

使用 OpenAI/DeepSeek 原生 **Tool Use API**（Function Calling）：

```json
// 请求时声明可用工具
{
  "tools": [
    {
      "type": "function",
      "function": {
        "name": "json_format",
        "description": "格式化输入的JSON文本",
        "parameters": {
          "type": "object",
          "properties": {
            "input": { "type": "string" }
          },
          "required": ["input"]
        }
      }
    },
    {
      "type": "function",
      "function": {
        "name": "read_file",
        "description": "读取指定文件内容",
        "parameters": {
          "type": "object",
          "properties": {
            "path": { "type": "string", "description": "绝对路径" }
          },
          "required": ["path"]
        }
      }
    }
  ],
  "tool_choice": "auto"
}

// AI 返回结构化 tool_calls，无需手写 parser
{
  "choices": [{
    "message": {
      "role": "assistant",
      "tool_calls": [{
        "id": "call_abc123",
        "type": "function",
        "function": {
          "name": "json_format",
          "arguments": "{\"input\": \"{\\\"name\\\":\\\"test\\\"}\"}"
        }
      }]
    }
  }]
}
```

### 2.3 收益

| Before（手写 Parser） | After（Function Calling） |
|---|---|
| 190 行 AgentPlanParser | 直接解析 API 返回的 JSON |
| AI 格式不稳定 → 需要容错 | AI 原生返回结构化数据 |
| ToolCatalog 和 API 工具描述不一致 | ToolCatalog 直接映射 API tools 参数 |
| 面试时需解释「为什么不用原生 API」 | 面试时自然引出 Function Calling 概念 |

## 三、上下文管理系统（Skills + Memory）

### 3.1 现状

Codex 有 SQLite 聊天记录，但没有 Agent 自身的「长期记忆 / 身份 / 技能」系统。WorkBuddy 的核心设计就是三层记忆 + 技能系统。

### 3.2 项目级指令文件（CODEX.md）

Agent 启动时自动读取并注入 system message：

```
C:\Users\97486\AIChatDesktop\CODEX.md
```

```markdown
# CODEX.md — Agent 启动指令

## 身份
你是 Codex 项目的 AI 开发助手。

## 编程规范
- 代码风格遵循 `.clang-format`，4 空格缩进
- 回答问题时优先给出可操作的代码示例
- 技术栈: C++17, Qt 6.10, MinGW, CMake

## 禁止
- 不直接修改构建产物目录 (build-*/)
- 不提交 API Key 或凭据到 Git
```

### 3.3 工作记忆层（AgentMemory）

建议新增 `src/memory/` 模块：

```
src/memory/
├── AgentMemory.h        # 抽象接口: remember() / recall() / forget()
└── AgentMemory.cpp      # SQLite 实现
```

**记录内容：**

- 用户明确说「记住这个」的内容
- Agent 自行总结的重要决策（如「用户偏好 Qt Widgets 而非 QML」）
- 项目级约定和历史偏好
- 未来可扩展向量相似度检索

**数据结构：**

```cpp
struct MemoryEntry {
    QString id;           // UUID
    QString category;     // "preference" / "decision" / "convention"
    QString content;      // 记忆文本
    QString source;       // 来源（用户明确 / Agent 自动总结）
    QDateTime createdAt;
    QDateTime lastAccessedAt;
};
```

### 3.4 技能系统（Skills）

类似 WorkBuddy 的 SKILL.md，建议新增 `src/skills/` 目录：

```
src/skills/
├── Skill.h              # 技能定义: name + instructions + requiredTools
├── SkillRegistry.h      # 扫描注册技能文件
└── examples/
    ├── build-release.skill.md
    ├── fix-compile-errors.skill.md
    └── json-format-workflow.skill.md
```

**技能文件示例（build-release.skill.md）：**

```markdown
# 构建 Codex Release 版本

## 描述
使用 CMake + MinGW 构建项目的 Release 可执行文件

## 步骤
1. cmake -S . -B build-release -DCMAKE_BUILD_TYPE=Release
2. cmake --build build-release
3. ctest --test-dir build-release --output-on-failure

## 需要的工具
- workspace.execute_command（V9 后可用）

## 风险等级
Low（仅构建，不修改源码或系统）
```

**收益**：Agent 不只是「能执行 N 个工具」，而是「N 个工具 × M 个技能组合」。

## 四、工具生态扩展

### 4.1 现状

V6 工具集：JSON 格式化/压缩、Markdown 空白清理、文本清理、文件读/列目录/保存/打开、Agent 计划生成。

### 4.2 新工具规划

| 工具类型 | 具体能力 | 优先级 | 建议阶段 |
|---|---|---|---|
| 文件操作增强 | 写文件、删除、重命名 | **P0** | V8 已规划 |
| 命令执行 | 白名单命令 (git, ctest, dir) | **P1** | V9 已规划 |
| 网页搜索 | WebSearch（类似 WorkBuddy） | **P1** | V9~V10 |
| 浏览器操作 | 截图、点击、填表 | P2 | V10+ |
| 代码审查 | git diff + AI review | P2 | V10+ |
| 数据处理 | CSV/Excel 读写 | P2 | V10+ |
| 发布打包 | windeployqt + 压缩 + GitHub Release | P2 | V10+ |
| 图片处理 | 格式转换、OCR 文字识别 | P3 | V11+ |

### 4.3 工具注册表模式

不要在 `AgentPlanExecutor` 里 `if-else` 硬编码工具，改为注册表模式：

```cpp
// AgentTool 抽象接口
class AgentTool {
public:
    virtual ~AgentTool() = default;
    virtual QString toolId() const = 0;
    virtual AgentToolDescriptor descriptor(AppLanguage lang) const = 0;
    virtual ToolResult execute(const QJsonObject &params) = 0;
};

// 工具注册表
class ToolRegistry {
public:
    void registerTool(std::unique_ptr<AgentTool> tool);
    ToolResult execute(const QString &toolId, const QJsonObject &params);
    QVector<AgentToolDescriptor> functionCallingTools() const;

private:
    QMap<QString, std::unique_ptr<AgentTool>> m_tools;
};
```

## 五、对话式 Agent 交互

### 5.1 现状问题

Agent 计划在独立对话框 `AgentPlanDialog` 中，用户点「确认」→ 执行 → 输出在对话框。与 Claude/WorkBuddy 的聊天式体验差距大——后者的工具调用结果直接嵌入聊天流。

### 5.2 目标体验

工具调用作为**聊天消息的一部分**展示：

```
用户: 帮我把桌面上的 data.json 格式化后保存到 agents/ 目录

AI:   正在分析你的需求...

     [步骤 1/3] read_file
     路径: C:\Users\97486\Desktop\data.json
     状态: ✓ 完成 (250KB)

     [步骤 2/3] json_format
     输入: (文件内容)
     状态: ✓ 完成 (1,203 行)

     [步骤 3/3] save_file
     路径: agents/data.json
     状态: ✓ 已保存

     ✅ 全部完成！文件已保存到 agents/data.json

用户: 把 agents 改成 output

AI:   [步骤 1/1] save_file
     路径: output/data.json
     状态: ✓ 已保存
```

关键特性：
- 用户可随时说「不对，改成 XXX」或「再试一次」
- `AgentPlanDialog` 可逐步被聊天内交互替代
- 工具调用状态以卡片形式嵌入消息流

## 六、安全架构增强

在 Agent Loop 模式下，需要额外的运行时安全层：

| 安全层 | 现状 | 建议增强 |
|---|---|---|
| **工具目录** | 静态注册，手动确认 | 运行时权限检查 `canExecute(toolId, params, context)` |
| **执行监控** | 无 | 超时监控 (30s/工具) + 步数上限 (5步) + 循环检测 |
| **注入防护** | TASK-006 规划中 | AI 回复自身也检测是否含「忽略安全规则」类指令 |
| **审计日志** | AppLogger 基础 | Agent 专用日志（工具调用链 + 参数摘要 + 决策理由） |
| **结果回传** | 用户确认后回传 | 文件内容标记为不可信数据，不能绕过本地策略 |
| **权限分级** | Risk 枚举 | 按操作类型动态计算风险（文件系统 > 文本处理 > 只读） |

### 9.1 各系统 Agent-计算机交互架构拆解

#### 9.1.1 Claude Code：最成熟的 Agentic Loop 实现

**核心循环（`queryLoop`）：**

```
while (true) {
    Snip/Microcompact/Collapse/Autocompact   ← 六层上下文管理
    ↓
    调用模型 API（流式输出）
    ↓
    ├─ 纯文本 → 执行 Stop Hooks → 退出循环
    └─ tool_use → StreamingToolExecutor 并行执行工具
        ├─ 只读工具：并发执行（max 10）
        ├─ 写入工具：串行排队
        └─ Bash 错误级联取消
    ↓
    tool_result 拼回消息数组 → 下一轮迭代
}
```

**关键设计：**

| 机制 | 实现方式 | Codex 差距 |
|------|---------|-----------|
| **流式工具执行** | 模型还在输出时就启动工具执行，不等 `message_stop` | Codex 必须等完整响应 |
| **并发工具** | `partitionToolCalls()` 分区，只读并发、写入串行 | 全部串行 |
| **上下文压缩** | 六层分级：Snip→Microcompact→Collapse→Auto Compact→Reactive→Manual | 无上下文管理 |
| **Multi-Agent** | Fork Subagent / Team Agent / Coordinator Mode / Dream Agent | 无 |
| **Token Budget** | 追踪每轮消耗，检测边际效益递减，提前终止 | 无 |
| **Prompt Cache** | Fork Agent 共享 cache key，占位符统一 | 无 |

**与计算机交互的方式：**
- 文件：`Read` / `Write` / `Edit` / `Glob` / `Grep`
- 命令：`Bash`（无限循环内，每轮可执行）
- 系统：通过 Bash 间接操作（不直接调 Win32 API）
- 浏览器：通过 MCP / Playwright 集成

#### 9.1.2 WorkBuddy：五层架构 + 双模运行

**五层逻辑架构：**

```
第五层  用户交互层     桌面客户端 / 微信 / 企微 / 飞书 / 钉钉
第四层  能力服务层     文件操作 / 数据处理 / 文档生成 / 图表制作
第三层  智能体底座层    NLU → 任务规划器 → 工具调用器 → 执行监控器
第二层  基础设施层     云端沙箱（腾讯云） / 本地执行（用户电脑）
第一层  安全与治理层    权限隔离沙箱 / 审计日志 / MCP 协议安全
```

**关键设计：**

| 机制 | 实现方式 | Codex 差距 |
|------|---------|-----------|
| **双模运行** | 云端沙箱（算力） + 本地执行（数据安全），可切换 | 仅本地 |
| **Skills 系统** | SKILL.md 文件 → 注入 system prompt → 模型按技能执行 | 已有基础版（V10.2） |

| **IM 远程控制** | 微信/企微/飞书/钉钉发消息 → 电脑执行 → 返回结果 | 无 |

**与计算机交互的方式：**
- 文件：直接读写本地文件系统（授权后）
- 命令：Shell/Bash 执行
- 浏览器：agent-browser skill → Playwright 自动化
- 桌面操作：通过工具集间接操作（非 Win32 直接调用）
- 远程：WebSocket 长连接 + IM 消息通道

**Agentic Loop 的 Prompt 层实现（从系统提示词推断）：**

```
<agent_loop>
1. Analyze context → 理解当前状态
2. Think → 推理下一步
3. Select tool → 选择工具
4. Execute action → 执行
5. Receive observation → 获取结果
6. Iterate → 循环，直到任务完成
</agent_loop>
```

核心和你当前 Codex 的 `AgentLoopController` 逻辑一致——区别在于 WorkBuddy 把它写进了 system prompt 让 AI 自己驱动，而你的 Codex 是 C++ 硬编码的状态机。

### 9.2 Agent 与 Windows 系统交互的三种模式

通过对四个系统的分析，Agent 与操作系统交互存在三种递进的模式：

#### 模式一：工具中介模式（Tool Mediated）← Codex 当前

```
Agent → 工具注册表 → 调用工具函数 → 返回结果 → Agent
         ↑
    AgentToolRegistry
    (workspace.*, git.*, command.*, data.*, etc.)
```

**特点：** Agent 不直接操作系统，通过预先注册的工具函数间接操作。每个工具函数的输入输出被严格定义。

**代表：** Codex V11、早期 Claude Code

#### 模式二：Shell 桥接模式（Shell Bridge）← WorkBuddy / Claude Code

```
Agent → Bash/Shell → 操作系统 → 返回 stdout/stderr → Agent
         ↑
    CommandRunner (white-list)
    或直接 Bash（有沙箱限制）
```

**特点：** Agent 通过 shell 命令与系统交互，工具注册表退化为权限控制层。Agent 可以执行任意白名单命令。

**代表：** WorkBuddy 的 Bash 模式、Claude Code 的 Bash 工具

#### 模式三：感知-操作闭环（Perception-Action Loop）← 最先进

```
Agent → 截图/窗口检测 → AI 分析画面 → 决策
  ↓                                          ↑
键鼠操作/窗口管理 → 系统状态变化 → 再次感知
```

**特点：** Agent 像人一样"看"屏幕、"操作"电脑，形成完整闭环。不需要 API、不需要 shell，直接像素级交互。

**代表：** OpenClaw 的 GUI Agent、WorkBuddy 的 computer use 能力

**三种模式的能力对比：**

| 游戏自动化 | ❌ | ❌ | ✅ |

### 9.4 Codex 追平的关键路径（三个必做 + 两个建议）

#### 必做一：上下文窗口管理（P0，1.5天）

这是当前最大的体验差距——消息多了直接报 API 413 错误。

**方案：新增 `ContextWindowManager`**

```
src/app/ContextWindowManager.h
src/app/ContextWindowManager.cpp
```

```cpp
class ContextWindowManager {
public:
    struct ContextBuildResult {
        QVector<ChatMessage> messages;  // 实际发送的消息
        int estimatedTokens;
        int originalCount;
        int trimmedCount;
        QString summary;                // 被裁剪部分的摘要
    };

    // 核心算法：
    // 1. 估算总 token
    // 2. 如果超标 → 从旧到新裁剪，保留 systemPrompt + 最近 N 轮
    // 3. 被裁剪部分调用 AI 生成一句话摘要，注入为系统消息
    ContextBuildResult build(
        const ChatSession &session,
        int maxTokens,
        const QString &systemPrompt
    );

    // 估算：中文 1 字 ≈ 2 token，英文 1 词 ≈ 1.3 token
    static int estimateTokens(const QString &text);
};
```

**工作量：** 1.5 天 | **不改变现有架构**，只在 `ApplicationController::sendMessage` 中插入一步。

参考 Claude Code 的六层压缩中最基础的一层（Snip + Auto Compact）。

#### 必做二：从有限循环升级为无限 Agentic Loop（P0，2天）

**当前 `AgentLoopController`：**

```
预生成 N 步计划 → for 循环逐步执行 → 结束
```

**改造后：**

```
while (未终止) {
    构建 Prompt（目标 + 当前状态 + 可用工具 + 上一步结果）
    ↓
    AI 返回下一步 toolId + parameters（单步，非全量）
    ↓
    执行 → 收集 ToolResult
    ↓
    ToolResult 拼入下一轮 Prompt
    ↓
    检测终止条件：AI 返回 done=true | maxSteps | 用户停止
}
```

**关键改动：**

| 文件 | 改动 | 说明 |
|------|------|------|
| `AgentPlanExecutor.cpp` | 新增 `executeLoop()` | 替代线性执行，改为 `while` 循环 |
| `AgentLoopPromptBuilder.cpp` | `buildLoopPrompt()` | 每步注入上一步结果 |
| `ApplicationController.cpp` | `runAgentLoop()` | 新的入口方法，不依赖预先生成计划 |

**工作量：** 2 天 | **改动控制在 `app/` 层**，不影响 UI 和工具层。

#### 必做三：Project-level 记忆系统 + Skills 增强（P0，2天）

**当前：** `AGENT.md` + `AGENT_MEMORY.md` + `skills/*.skill.md`（V10 已有基础）

**改造：** 把 WorkBuddy 的三层记忆模式引入：

```
~/.codex/MEMORY.md          ← 用户级全局记忆（跨项目偏好）
.workbuddy/memory/MEMORY.md ← 项目级记忆（技术决策、约定）
.workbuddy/memory/YYYY-MM-DD.md ← 每日工作日志
```

**新增类：**

```cpp
class ProjectMemoryManager {
```

**工作量：** 2 天 | 已有多层记忆的基础设施，主要是读取/写入规则的标准化。

#### 建议一：Hook 插件系统（P2，3天）

参考 OpenClaw 的 14 个钩子点，给 Codex 增加最核心的 5 个：

```cpp
class AgentHookManager {
public:
    // 工具调用前拦截（修改参数、拒绝执行）
    virtual bool beforeToolCall(const QString &toolId, QJsonObject &params);
    
    // 工具执行后处理（脱敏、截断、格式化）
    virtual void afterToolCall(const QString &toolId, ToolResult &result);
    
    // Prompt 构建前注入上下文
    virtual QString beforePromptBuild();
    
    // Agent 循环结束后处理
    virtual void afterAgentLoop(const AgentLoopResult &result);
    
    // 会话开始/结束
    virtual void onSessionStart(const QString &sessionId);
    virtual void onSessionEnd(const QString &sessionId);
};
```

**收益：** 不修改核心代码就能扩展行为——比如加一个 `beforeToolCall` 把所有 `git.*` 操作记录到审计日志。

### 9.6 一句话总结

> **Agent 与计算机交互的本质不是"有多少个工具"，而是"Agentic Loop 如何把工具结果变成下一步的输入"。**
>
> Claude Code、WorkBuddy、OpenClaw 的共性：**一个永不停止的 while 循环，每轮把工具结果喂回 AI，AI 再决定下一步。**
>
> 你的 Codex 已经有 `AgentLoopController`（循环骨架）、`AgentPlanExecutor`（工具执行）、`StreamParser`（流式解析）——缺的是**上下文管理**（消息无限膨胀导致 API 报错）和**无限循环的 Prompt 组装逻辑**（当前循环有硬上限 2 轮）。
>
> **追平的核心工作只有三个：上下文管理 + 无限循环 + 记忆系统。这三个做完，架构层面就与 WorkBuddy/OpenClaw 同一梯队。**

## 十一、单机游戏逆向与内容修改

### 11.1 边界声明

| 场景 | 态度 |
|---|---|
| **自己玩的单机游戏**，做 mod/修改器 | ✅ 可行，类似 Cheat Engine / NexusMods |
| **有反作弊的多人在线游戏**（VAC/EAC/BattlEye） | ❌ 绝对不碰——账号封禁 + 法律风险 |
| **分享给他人用于在线游戏作弊** | ❌ 非法，不考虑 |

你问的"单机游戏"在这个框架内。本质上是把 Codex 做成**带 AI 助手的 Cheat Engine**。

### 11.2 三条技术路径

| 方式 | 原理 | 难度 | 稳定性 | 适用场景 |
|---|---|---|---|---|
| **内存读写** | `Read/WriteProcessMemory` 直接改内存 | ⭐⭐ | 每次更新偏移可能变 | 修改金币/血量/道具数量 |
| **DLL 注入 + Hook** | 注入 DLL → Hook 关键函数 → 修改参数/返回值 | ⭐⭐⭐⭐ | 相对稳定（函数签名不变） | 改伤害倍率/移速/掉落率 |
| **代码注入/Cave** | 在游戏内存中写入自定义汇编代码 | ⭐⭐⭐⭐⭐ | 极不稳定 | 深度魔改（不推荐起步） |

**推荐顺序**：先用 Cheat Engine 找偏移 → 验证内存读写可行 → 再考虑 DLL 注入。

### 11.5 DLL 注入实现

```cpp
class GameInjector {
public:
    bool injectDLL(DWORD pid, const QString &dllPath);
    bool injectViaManualMap(DWORD pid, const QString &dllPath);  // 绕过检测
    bool ejectDLL(DWORD pid, const QString &dllName);

private:
    // CreateRemoteThread + LoadLibrary（标准方式）
    bool injectViaCreateRemoteThread(DWORD pid, const QString &dllPath) {
        HANDLE hProcess = OpenProcess(
            PROCESS_CREATE_THREAD | PROCESS_VM_WRITE | 
            PROCESS_VM_OPERATION | PROCESS_QUERY_INFORMATION,
            FALSE, pid);

        // 在目标进程分配内存存放 DLL 路径
        size_t pathLen = (dllPath.size() + 1) * sizeof(wchar_t);
        LPVOID remotePath = VirtualAllocEx(
            hProcess, nullptr, pathLen, MEM_COMMIT, PAGE_READWRITE);
        WriteProcessMemory(hProcess, remotePath, 
                          dllPath.utf16(), pathLen, nullptr);

        // 创建远程线程调用 LoadLibraryW
        auto loadLibrary = (LPTHREAD_START_ROUTINE)GetProcAddress(
            GetModuleHandleW(L"kernel32.dll"), "LoadLibraryW");
        HANDLE hThread = CreateRemoteThread(
            hProcess, nullptr, 0, loadLibrary, remotePath, 0, nullptr);
        
        WaitForSingleObject(hThread, INFINITE);
        VirtualFreeEx(hProcess, remotePath, 0, MEM_RELEASE);
        CloseHandle(hThread);
        CloseHandle(hProcess);
        return true;
    }
};
```

```
    → 剩余 2 个可能性最高的地址

AI: "找到 2 个候选地址。我先尝试修改第一个..."
    写入 → OCR 验证画面 → 金币确实变了 ✓
    → 保存到 GameOffsetsDatabase

AI: "偏移已保存。下次直接改。"
```

### 11.11 技术难点与对策

| 难点 | 对策 |
|---|---|
| 游戏更新后偏移改变 | Pattern scan 搜索特征码，不依赖固定地址 |
| 64 位游戏地址空间巨大 | 先搜变化值，多次缩小范围（Cheat Engine 做法） |
| ASLR 地址随机化 | 不影响——基于运行时的实际地址，每次重新计算 |
| DEP 内存保护 | `VirtualProtectEx` 修改目标内存页属性 |
| 加壳游戏（VMProtect） | 极大增加难度，需要在解压后扫描；**不建议起步** |
| 金币数据加密存储 | 逆向加密算法；或直接 Hook 获取函数而非修改数据 |
| DLL 签名检测 | 单机一般不检测；有的话用手动映射注入 |

### 11.12 起步路径

```
Week 1: 纯内存读写（不注入 DLL）
  - GameMemoryScanner + GameMemoryPatcher
  - 用手动 Cheat Engine 预先找一个游戏的偏移
  - 在 Codex 中重现 CE 的基础扫描流程

Week 2: AI 辅助扫描
  - AI 指导用户交互（"花点金币再回来"）
  - 根据数值变化缩小地址范围
  - AI 对候选地址做合理性判断

Week 3: 偏移数据库
  - SQLite 存储 → 下次同一游戏自动加载
  - 支持版本匹配和回退

Week 4: DLL 注入原型（可选）
  - 先用记事本.exe 练手（安全）
  - 注入 DLL → Hook 一个函数 → 验证
  - 再迁移到实际游戏
```

## 十二、对话能力与交互体验优化

对标 ChatGPT / Claude / DeepSeek Chat 等主流 AI 聊天应用的成熟体验，识别当前 Codex 在对话能力和交互体验上的差距。

### 12.1 对话能力缺陷

#### 12.1.1 消息编辑 + 重新生成

**当前：** 消息发出后不能改，AI 回复不满意只能删除整个会话重来。

**目标：**

```
用户: "帮我写一个排序算法"
AI:   "void sort(...) { ... }"  ← 冒泡排序，不满意

→ 用户编辑自己的消息："帮我写一个快速排序，要带注释"
→ 自动重新生成 AI 回复
→ 原 AI 回复保留为 "版本 1"，新回复为 "版本 2"
→ 可左右切换查看不同版本
```

**数据结构改动：**

```cpp
struct ChatMessage {
    // ... 现有字段 ...
    QString parentMessageId;      // 如果是重新生成，指向原消息
    int version = 1;              // 版本号
    bool isReplaced = false;      // 被新版本替代
};
```

`ChatHistoryStorage` 不需要改表结构——同一 `session_id` 下多存几条 `ChatMessage`，`version` 字段区分。工作量约 1 天。

#### 12.1.2 上下文窗口管理

**当前：** 无限追加历史消息到 API 请求，超过 token 限制直接报错。用户完全不知道当前用了多少 token、还剩多少。

**目标：**

```
┌──────────────────────────────────────────┐
│ 上下文: 3,200 / 8,192 tokens (39%)        │
│ 已自动压缩 12 轮早期对话为摘要             │
└──────────────────────────────────────────┘
```

**新增类：`ContextWindowManager`**

```cpp
class ContextWindowManager {
public:
    struct ContextBuildResult {
        QVector<ChatMessage> effectiveMessages;  // 实际发送的消息
        int estimatedTokens;
        int originalMessageCount;
        int trimmedMessageCount;
        QString summary;  // 被裁剪内容的 AI 摘要
    };
    
    ContextBuildResult buildContext(
        const ChatSession &session,
        int maxTokens,
        const QString &systemPrompt
    );
    
    // Token 估算: 中文 1 字 ≈ 2 tokens, 英文 1 词 ≈ 1.3 tokens
    static int estimateTokens(const QString &text);
};
```

核心逻辑：超过限制时保留 `systemPrompt + 最近 N 轮 + 摘要`，被裁剪部分调用 AI 生成一句摘要注入上下文。

**工作量：** 约 1.5 天。

#### 12.1.3 对话分叉（Branching）

**当前：** 对话是线性的，不能从中间分叉。

**目标：**

```
         用户: 推荐一个框架
           ├── AI: 推荐 React (版本 1)
           │     └── 用户: 那 Vue 呢？       ← 分叉 A
           │
           └── AI: 说说 Flutter (版本 2)      ← 分叉 B（从同一位置分支）
```

**实现：** `ChatMessage.parentMessageId` 构建树形关系。同一消息可以有多个子节点。UI 上在可分支的消息旁加「从这分叉」按钮。工作量约 2 天。

#### 12.1.4 引用回复

**当前：** 无法引用之前的消息回复，多轮对话中容易混淆。

**目标：**

```
AI 消息下方操作栏: [📋 复制] [🔄 重新生成] [💬 引用回复]

点击引用回复 → 输入框中显示被引用的消息卡片
输入回复 → 发送时附带引用 ID
```

### 12.2 交互体验缺陷

#### 12.2.1 全局快捷键

**工作量：** 纯 `QShortcut` 注册，约 0.5 天。

#### 12.2.2 命令面板

`Ctrl+K` 呼出，模糊搜索匹配所有操作：

#### 12.2.3 输入区增强

### 12.3 数据能力缺陷

#### 12.3.1 全文搜索聊天记录

**当前：** `ChatHistoryStorage` 只支持按会话标题搜索，不能搜消息内容。

**方案 1（轻量）：** SQLite `LIKE` 模糊搜索。

```sql
SELECT m.content, m.session_id, s.title
FROM messages m JOIN sessions s ON m.session_id = s.id
WHERE m.content LIKE '%搜索词%'
ORDER BY m.created_at DESC LIMIT 50;
```

**方案 2（大场景）：** FTS5 全文索引。

```sql
CREATE VIRTUAL TABLE messages_fts USING fts5(content, session_id);
```

**UI：** `Ctrl+Shift+F` 呼出搜索窗口 → 显示匹配片段 + 所在会话名 + 点击跳转到该位置。

#### 12.3.2 会话分类增强

V5 已有收藏/归档/筛选。在此基础上增加：

```cpp
struct ChatSession {
    QSet<QString> tags;       // {"面试", "C++", "Qt"}
    QDateTime lastAccessedAt; // 按最近访问排序
};

// 侧栏分组视图
const auto favorites  = sessions.where([](auto &s) { return s.isFavorited; });
const auto recent     = sessions.orderBy("lastAccessedAt DESC").limit(10);
const auto byTag      = sessions.groupBy("tags");
const auto archived   = sessions.where([](auto &s) { return s.isArchived; });
```

| 优先级 | 能力 | 工作量 | 不变架构 | 理由 |
|---|---|---|---|---|
| **P0** | 消息编辑 + 重新生成 | 1 天 | ChatMessage 加字段 | 最常用操作 |
